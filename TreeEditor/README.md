# Tree Editor

A web app with two tree views. **DBTreeView** browses a large tree stored in PostgreSQL, loading it lazily. **CachedTreeView** is a local cache where you edit nodes before applying the changes to the database.

## Quick start

Requirements: Docker Desktop.

```bash
cd TreeEditor/backend
docker compose up --build
```

| Service    | URL                                                              |
|------------|------------------------------------------------------------------|
| UI         | http://localhost:5173                                            |
| API        | http://localhost:8080 (Swagger: http://localhost:8080/swagger)   |
| PostgreSQL | localhost:5434 (`treeeditor` / `treeeditor`)                     |

When the API starts, it applies EF migrations and seeds the sample data.

### Local development (without containers for API/UI)

```bash
cd TreeEditor/backend
docker compose up -d postgres
dotnet run --project TreeEditor/TreeEditor.csproj --launch-profile http   # API on :5272

cd ../frontend
npm install
npm run dev                                                               # UI on :5173, /api proxied to :5272
```

Frontend checks: `npm run lint`, `npm test`, `npm run build`.

## Database schema

One adjacency-list table:

| Column      | Type           | Notes                                                    |
|-------------|----------------|----------------------------------------------------------|
| `Id`        | `uuid` PK      | Generated by the client, so new nodes can be created offline in the cache |
| `ParentId`  | `uuid` NULL    | FK → `tree_nodes.Id`, `ON DELETE CASCADE`, indexed       |
| `Value`     | `varchar(500)` | Required, trimmed                                        |
| `Version`   | `bigint`       | Optimistic concurrency token, incremented when `Value` changes |

- The API only reads one level at a time: `GET /api/tree/roots` and `GET /api/tree/nodes/{id}/children` (paged, with `hasChildren` and `hasMore`). The whole tree is never loaded.
- Deletes use the database's self-referencing cascade, so descendants that were never loaded are deleted too.
- The API has no operation that changes `ParentId`, so existing parent–child relationships cannot be changed.
- `POST /api/tree/apply` runs updates, creates and deletes in one transaction. A stale `version` returns `409 Conflict`.

## Frontend

React 19, TypeScript, Vite, Feature-Sliced Design, jotai (cache persisted to `localStorage`), TanStack Query (DB reads), MUI and MUI X Tree View, Tailwind CSS.

```
src/
  app/       providers, global styles, notifications
  pages/     tree-editor
  widgets/   db-tree-view, cached-tree-view
  features/  load-to-cache, edit-node, add-child, delete-node, apply-changes, reset-app
  entities/  db-node (queries, selection), cached-node (cache model and pure logic)
  shared/    api client, dialogs, panel
```

### Key decisions

- **The cache only talks to the database on Load and Apply.** Load needs no request, because DBTreeView has already fetched the node.
- **Each cached node stores its full ancestor path (`ancestorIds`).** DBTreeView loads top-down, so every visible node's path is already in the query cache. The path makes these cases work:
  - Deleting a node also marks as deleted any cached descendants, even when the nodes between them were never loaded.
  - A node loaded under an ancestor that is deleted but not yet applied appears as deleted immediately.
- **Hierarchy.** Nodes are nested by `parentId`. A node whose parent isn't cached is shown as a root. When the parent is loaded, the node moves under it.
- **Apply sends only the topmost deleted nodes.** The database cascade removes their descendants. A separate delete for a descendant would find no row and cause a conflict. Nodes that were created and then deleted locally are never sent.
- **Versions after Apply are computed on the client**, using the same rule as the backend: new nodes get 1, and an edited node's version goes up by 1. Changed DB levels are then re-fetched.
- **Deleted nodes** stay in the cache, crossed out, and can't be edited.
- **Persistence.** The cache survives page reloads. Reset clears it together with the database.
